# Travel Platform ↔ Odoo CRM/CMS Integration Architecture

## IMPLEMENTATION PROMPT

You are acting as a **Senior Software Architect + Senior Python/Odoo Engineer**.

Your task is to design and implement the integration architecture between:

1. Public Travel Platform
2. Odoo CRM + CMS Back-office
3. External data sources

The final goal is to make Odoo operate on **REAL DATA** generated by the public website and other external channels, while keeping the public platform independent from Odoo.

This is **NOT** a task to merge Odoo into the public website.
This is **NOT** a task to let Odoo render public pages.
This is **NOT** a task to share databases between Django and Odoo.

# 4. AUTHORING MODEL VS SERVING MODEL

It is acceptable and intentional for similar entities to exist in both systems.

Example:

```text
Odoo:
travel.place

Django:
Place
```

These are not the same model.

Odoo `travel.place` is an **AUTHORING MODEL** and may contain:

```text
draft content
reviewer
workflow state
internal note
revision
approval history
```

Django `Place` is a **SERVING MODEL** and may contain:

```text
public content
PostGIS location
search fields
public rating
recommendation attributes
embedding/index references
SEO fields
```

Do NOT attempt to force both systems into the same schema.

# 6. CANONICAL DATA CONTRACT

External sources must NOT directly control internal Odoo/Django models.

Every external payload must first be transformed into a canonical structure.

Example external lead:

```json
{
  "name": "Nguyen Van A",
  "phone": "098xxxxxxx",
  "source": "facebook",
  "product": "Vung Tau Tour"
}
```

Normalize into:

```json
{
  "event_id": "evt_xxx",
  "event_type": "lead.created",
  "event_version": 1,
  "source": "facebook",
  "occurred_at": "2026-10-05T10:00:00Z",
  "external_id": "FB-829128",
  "data": {
    "customer": {
      "name": "Nguyen Van A",
      "phone": "8498xxxxxxx"
    },
    "interest": {
      "type": "tour",
      "reference": "vung-tau-tour"
    }
  }
}
```

All providers must eventually map to canonical contracts.

# 44. DEFINITION OF DONE FOR MVP

The integration MVP is complete only when the following can be demonstrated using **REAL application data**:

1. A traveler submits an inquiry on the public website.
2. Django stores it successfully.
3. Customer deduplication executes.
4. An integration event is created.
5. Odoo receives the event.
6. A real Odoo CRM lead is created.
7. Source attribution is preserved.
8. Duplicate delivery does not duplicate the lead.
9. Integration status is observable.
10. An editor creates/updates content in Odoo CMS.
11. An authorized reviewer publishes it.
12. Odoo sends a signed integration event.
13. Django receives and validates it.
14. Public serving data is updated.
15. Search/cache/index update occurs where applicable.
16. The public website displays the new data.
17. Duplicate events do not duplicate or corrupt content.
18. Odoo downtime does not break public browsing.

> **Plug new systems into the platform**

rather than:

> **Rewrite the platform whenever a new integration is needed.**
